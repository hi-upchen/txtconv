# 服務壞掉時通知我（Alerting）— txtconv 設計

**日期：** 2026-10-19 初稿，2026-10-20 改版
**狀態：** 站長授權由 Fable 5 代為決定細節（2026-10-20）。本版即為定案，接著寫實作計畫。
**最新變更（2026-10-20）：**
- 拿掉 Telegram，全部改走 UptimeRobot 的 email 和 iPhone 推播。這是站長在 jars.money 定下的偏好，txtconv 照辦。
- 健康檢查頁分組，每組一個監控。
- ECPay 結帳已合併，加上付款相關的檢查。

**來源：**
- 做法和陷阱：`~/.claude/knowledge/vercel-alerting-playbook.md`。
- 原則：`~/.claude/knowledge/alerting-design-best-practices.md` 和 `~/.claude/knowledge/health-check-best-practices.md`。
- 照抄的程式：jars.money 的 `monitor-groups` 分支，合併後以 `master` 為準。

## 1. 目標

txtconv 的服務壞掉時，站長會在幾分鐘內收到 UptimeRobot 的 email 和手機推播。平常不發任何訊息，也不發每日或每週報告。

所有「需要站長處理」的故障，都會讓某個健康檢查回 `fail`。UptimeRobot 看到 503 就通知。程式本身不發任何通知。

**為什麼現在做：**
- 2026-10-05 Vercel 停用了所有檔庫，自訂字典因此壞掉。程式沒有報任何錯，使用者的自訂詞默默失效，轉換結果只套用 OpenCC 預設。這件事是事後才發現的。
- 2026-10-16 jars.money 的語意分析服務停了約 20 小時，也是站長自己看到才發現。
- 2026-10-20 ECPay 結帳上線，現在是唯一的購買管道。「客人付了錢卻沒拿到終身版」必須馬上知道。

## 2. txtconv 的特點

- **免費版的轉換全在使用者的瀏覽器裡跑。** 伺服器負責的只有登入、自訂字典和付款。
- **沒有排程工作。** 不需要 jars.money 的排程紀錄和 `jobs` 組。
- **資料庫是 Supabase。** 存取一律用現有的 `createServiceClient`。
- **最大的風險是「壞了卻不報錯」。** 讀不到字典檔時，`app/api/dictionary/route.ts` 和 `lib/client-converter.ts` 都直接回空字典。

## 3. 監控設計

### 3.1 UptimeRobot：四個監控 [新建]

帳號是站長的個人帳號 hi.upchen@gmail.com。四個監控都是每 5 分鐘一次、只接受 2xx。出事時同時通知 email（編號 8694945）和 iPhone 推播（編號 8935319）。

| 監控名稱 | 網址 | 抓到什麼 |
|---|---|---|
| `txtconv home` | `https://txtconv.arpuli.com/` | 整站掛掉、Vercel 暫停專案、頁面算繪錯誤 |
| `txtconv core` | `/api/health?key=…&group=core` | 資料庫、登入服務、字典檔庫 |
| `txtconv payments` | `/api/health?key=…&group=payments` | 付款設定錯誤、付了錢沒開通、付兩次 |
| `txtconv callbacks` | `/api/health?key=…&group=callbacks` | 24 小時內有付款回呼失敗 |

分組的原因：
- 推播的名稱直接說明哪裡壞了。
- 一組一直壞著，不會蓋掉另一組新出的問題。
- 付款回呼失敗會讓檢查壞 24 小時。UptimeRobot 只在狀態改變時通知。如果它跟 `paidOrders` 同組，這 24 小時內新出的「付了錢沒開通」就不會通知。所以它自己一組。

UptimeRobot 只在「變壞」和「恢復」各通知一次，所以不需要節流。

### 3.2 健康檢查頁 `/api/health` [新建]

照抄 jars.money 分組版的 `src/app/api/health/route.ts`：
- 網址要帶 `?key=<HEALTH_CHECK_KEY>`。金鑰錯誤或沒帶時回 401，不透露任何內容。比對用固定時間的方式。
- `group` 是 `core`、`payments` 或 `callbacks`。不認得的組別回 400，所以監控網址打錯也會通知。沒帶組別就跑全部檢查，方便手動查看。
- 狀態只有 `pass` 和 `fail`，沒有 `warn`。有任何 `fail` 就回 503，否則回 200。
- 回應格式是 `application/health+json`。失敗的項目附上原因和修理提示。
- 每項檢查並行執行，各自 8 秒逾時。逾時或丟錯誤都算 `fail`。
- 每組結果快取 60 秒。同時進來的請求共用同一次計算。
- 必須宣告 `export const dynamic = 'force-dynamic'`。
- 錯誤原因輸出前，遮蔽所有密鑰的值。
- 每個回應都帶 `Cache-Control: no-store`，瀏覽器和中間的快取都不能留副本。

### 3.3 `core` 組

| 名稱 | 怎麼查 | 失敗時的修理提示 |
|---|---|---|
| `database` | 用服務金鑰讀 `profiles` 的一列 id。沒有錯誤就通過 | 到 Supabase 後台查專案狀態（是否被暫停、是否超過用量） |
| `auth` | 帶公開的 anon 金鑰呼叫 `GET <SUPABASE_URL>/auth/v1/settings`。回 200，而且 `external.google` 和 `external.email` 都是 `true` 才通過。2026-10-19 已用 curl 確認這兩個欄位存在 | 到 Supabase → Authentication → Providers 打開 Google 或 Email |
| `dictionaryStore` | 用 `@vercel/blob` 的 `list({ limit: 1, prefix: 'dictionaries/' })` 取一個檔，再用 `fetch` 對它的網址送 `HEAD` 請求（`cache: 'no-store'`），回 200 才通過。`HEAD` 只問檔案在不在，不下載內容。檔庫裡沒有任何字典檔也算通過 | 到 Vercel → Storage 查 `txtconv-prod-dictionaries` 是否被停用，以及帳單和用量 |

`auth` 是唯一碰到 Supabase 登入服務的檢查。`database` 走的是另一個服務，登入服務壞了它照樣通過。

`dictionaryStore` 只讀不寫。「只有字典 API 能寫檔庫」的測試（`__tests__/guards/blob-write-guard.test.ts`）把 `list` 當成讀取，不必修改。

### 3.4 `payments` 組

| 名稱 | 怎麼查 | 失敗時的修理提示 |
|---|---|---|
| `paymentConfig` | 只在 Vercel 正式環境（`VERCEL_ENV=production`）檢查，其他環境直接通過。兩個都成立才通過：`getEcpayConfig()` 不丟錯誤；`NEXT_PUBLIC_APP_URL` 等於 `https://txtconv.arpuli.com` | 照維運手冊「三、合併上線前檢查」第 1 步補齊 Vercel 正式環境變數 |
| `paidOrders` | 維運手冊的對帳查詢 A：狀態是 `paid`，但帳號不是終身版的訂單。有任何一筆就失敗，原因列出筆數和訂單編號 | 照維運手冊「二、對帳查詢」A 手動開通 |
| `doublePaid` | 維運手冊的對帳查詢 B：同一個使用者有兩筆以上 `paid` 訂單。有就失敗，原因列出訂單編號 | 照維運手冊「二、對帳查詢」B 退款，再把多的那筆標成 `refunded` |

**`paymentConfig` 為什麼要查網址：**
- 程式在 `ECPAY_ENV` 設錯時會拒絕結帳（fail closed），但網址設錯時不會。
- 付款通知的網址由 `NEXT_PUBLIC_APP_URL` 組成。網址錯了，每一筆付款通知都會送到別的地方。
- 結果是客人付了錢，訂單卻一直停在 `pending`，任何對帳查詢都看不到。

**`paidOrders` 和 `doublePaid` 會一直失敗，直到站長處理完。** 這是刻意的：
- 處理完，監控恢復正常，就等於確認收到。
- 它們在 `payments` 組，不會蓋掉 `core` 組的問題。
- `ecpay_orders` 和 `profiles` 之間沒有外鍵，資料庫 API 不能直接合併查詢。所以分成兩次小查詢，在程式裡比對：
  - 第一次讀所有 `paid` 訂單。
  - 第二次讀所有終身版帳號的 id（`license_type = 'lifetime'`）。
- 資料庫 API 每次最多回 1000 筆。任一次查詢回了 1000 筆以上，結果可能不完整。這時 `paidOrders` 直接失敗，原因是「資料超過 1000 筆，請改用 SQL 對帳查詢」。

### 3.5 `callbacks` 組

| 名稱 | 怎麼查 | 失敗時的修理提示 |
|---|---|---|
| `callbackFailures` | 新表 `ecpay_callback_failures` 裡有 24 小時內的紀錄就失敗。原因列出最近一筆的原因和訂單編號 | 查 Vercel 紀錄 "ecpay/callback"，再到綠界後台核對這筆訂單 |

這一組自己一個監控，原因見 3.1 節。紀錄 24 小時後自動不算。站長查完想提早恢復，可以刪掉紀錄，步驟在維運手冊「四、監控」。

### 3.6 ECPay 付款回呼要記錄的失敗

檔案：`app/api/payment/ecpay/callback/route.ts`。回給 ECPay 的內容一律不變。

**要記錄的情況：** 簽章已驗證、`RtnCode` 是 1，代表錢已經付了，之後卻失敗：
| 情況 | 記錄的原因 |
|---|---|
| 缺訂單編號 | 付款回呼缺訂單編號 |
| 找不到訂單 | 付款訂單找不到（或資料庫查詢失敗） |
| 金額不符 | 付款金額不符 |
| 查到訂單後又不見 | 付款訂單找不到（或資料庫查詢失敗） |
| 意外錯誤（catch 區塊） | 付款回呼發生錯誤 |

查訂單的函式在資料庫出錯時也回「找不到」。所以「找不到訂單」的原因寫明可能是資料庫查詢失敗。

這幾種情況都沒有任何訂單被標成已付款，所以對帳查詢看不到，只能另外記錄。

**怎麼記錄：**
- 只有正式商店（`ECPAY_ENV=production`）會寫紀錄。這個判斷放在 `recordPaymentFailure` 裡，只有一處。
  - 原因：預覽和本機用的是公開的測試商店金鑰，卻共用正式資料庫。
  - 任何人都能用測試金鑰簽一個假回呼。不擋的話，假回呼或測試回呼會讓正式監控變紅。
- 在新表 `ecpay_callback_failures` 寫入一列：原因和訂單編號。不寫 email，也不寫使用者編號。
- 照抄 jars.money 的 `paymentFailures.ts`，用 `after()` 寫入。先回應 ECPay，再寫紀錄。
- 寫入永遠不丟錯誤。失敗只寫一行紀錄。
- catch 區塊只在一個條件下記錄：`signatureVerified` 旗標已經設定。簽章驗證之前就丟出的錯誤（例如掃描程式送來的亂碼）不記錄。

**不記錄的情況：**
- 簽章驗證失敗：只寫紀錄。任何人都能亂送請求，不能讓陌生人讓監控變成故障。
- 客人自己刷卡失敗（`RtnCode` 不是 1）。
- 模擬付款、測試商店、已退款訂單：都會回 `1|OK` 確認，但不開通。這是設計好的結果。
- 開通失敗：訂單已是 `paid`，帳號不是終身版，`paidOrders` 會抓到。
- 付了兩次：`doublePaid` 會抓到。

## 4. 刻意不做與已知缺口

**不做：**
- Telegram 或任何程式自己發的通知。
- Sentry 或紀錄轉送服務。
- 每日或每週報告。
- Gumroad webhook 的監控。Gumroad 已不賣東西。資料庫壞了由 `database` 抓到。
- 個別使用者讀不到字典時通知。整個檔庫壞了由 `dictionaryStore` 抓到。
- 每 5 分鐘在真的瀏覽器裡跑一次轉換的監控。太重了。
- 做成套件和 jars.money 共用。照抄比維護套件便宜。

**已知缺口，接受：**
- **付款通知完全沒送到伺服器**（例如綠界那邊故障超過它一天的重試時間）：錢付了，訂單停在 `pending`，看起來跟「放棄結帳」一樣。只能靠客人來信，或綠界後台。
- **網頁回 200，但轉換程式在瀏覽器裡當掉。** 目前 CI 只跑建置和單元測試。把端對端測試加進 CI 是另一件工作。
- **Google 登入失敗。** Google 按鈕在瀏覽器裡完成登入，伺服器看不到。`auth` 只能確認 Supabase 那一端的 Google 開著。
- **寄驗證碼信失敗或超過寄信額度。** 寄信是瀏覽器直接呼叫 Supabase，伺服器看不到。
- **UptimeRobot 和 txtconv 同時壞掉。** 這時收不到通知。
- **GA4 和 GTM 的事件遺失、轉換品質。** 不算「服務壞掉」。

## 5. 需要新增的資源

- **環境變數 [新建]：** 只有 `HEALTH_CHECK_KEY`。
  - 隨機產生，設在 Vercel 正式環境。
  - 存進 1Password `Indie-Secrets` 裡 txtconv 的項目，欄位名 `health-check-key`。
  - 預覽環境不設。沒設定時，所有請求都回 401。
- **資料表 [新建]：** `ecpay_callback_failures`。
  - 欄位：`id uuid primary key default gen_random_uuid()`、`created_at timestamptz not null default now()`、`reason text not null`、`merchant_trade_no text`。
  - 開啟 row-level security，不加任何規則，跟 `ecpay_orders` 一樣。只有服務金鑰能讀寫。
  - 檔案放 `supabase/migrations/20261020_ecpay_callback_failures.sql`。
  - 用 Supabase Management API 套用。金鑰在 1Password `supabase-txtconv/access-token`。行不通時，改貼到 Supabase SQL 編輯器執行。
- **UptimeRobot 監控 [新建]：** 3.1 節的四個。

## 6. 測試與驗收

**單元測試：**
- 健康檢查頁：
  - 金鑰錯誤回 401，不認得的組別回 400。
  - 三組各自只跑自己的檢查。只有付款回呼失敗時，`payments` 組仍是 200。
  - 每個回應都帶 `Cache-Control: no-store`。
  - `fail` 回 503。
  - 每組快取 60 秒。
  - 逾時算 `fail`。
  - 錯誤原因裡沒有密鑰。
- 每項檢查：成功、失敗各一個測試。
- 付款回呼：
  - 五種要記錄的失敗，各寫一筆紀錄。
  - 只有 `ECPAY_ENV=production` 時才寫；沒設定或是 `sandbox` 時不寫。
  - 亂送的請求和簽章驗證前的錯誤，什麼都不寫。
  - 回給 ECPay 的內容完全不變。

**本機實測：** 用真的服務啟動開發伺服器，再用 `curl` 打：
- 不帶金鑰回 401，錯誤的組別回 400。
- `core`、`payments`、`callbacks` 都回 200，內容型別是 `application/health+json`。
- 故意弄壞一項，例如設錯 Supabase 網址，那一組回 503，而且原因裡沒有任何密鑰。

**上線（站長已授權，照手冊順序）：**
1. 套用資料表。
2. 在 Vercel 正式環境設定 `HEALTH_CHECK_KEY`。
3. 開合併請求、合併、等 Vercel 部署完成。
4. 用 curl 打正式網站的三組，都是 200。
5. 建立四個 UptimeRobot 監控。
6. 送達測試：
   - 暫時建一個一定會失敗的監控，例如不帶金鑰的健康檢查網址，它會回 401。
   - 等它變成故障，確認 email 和推播都收到。
   - 刪掉這個暫時的監控。
7. 確認四個監控都是「正常」。

## 8. 代站長做的決定（Fable 5，2026-10-20）

- 拿掉 Telegram，所有故障都經由健康檢查和 UptimeRobot 通知。
- 三組健康檢查（`core`、`payments`、`callbacks`）加上首頁，共四個監控。
- 字典檔庫的檢查改用「列出一個檔，再用 `HEAD` 確認它讀得到」，不用手動上傳測試檔。
- 對帳查詢 A 和 B 都是 `payments` 組的檢查，處理完才恢復。
- 付款回呼失敗自己一組（`callbacks`）。紀錄 24 小時後自動恢復，也可以手動刪掉提早恢復。
- 只有正式商店的付款回呼會寫失敗紀錄。
- 簽章驗證失敗只寫執行紀錄，不寫失敗紀錄，不影響監控。
- 不監控 Gumroad 和個別使用者的字典讀取。
